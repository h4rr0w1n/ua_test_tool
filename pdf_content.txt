1 INTRODUCTION
1.1 PURPOSE OF THE DOCUMENT
The purpose of the document is to define the functional requirements for AMHS/SWIM Gateway testing
procedures.
1.2 DOCUMENT STRUCTURE
Chapter 2 deals with the scope of functions to be tested at SWIM implementations which should be
accessible for testing. In addition, the used transport service for SWIM communications is identified and the
interface with AMHS at the implemented AMHS/SWIM Gateway is detailed.
Chapter 3 defines the scope of the test environment used for conformance testing. Related test
configurations are added with explanations on sequences of exchanged AMHS and SWIM messages. In
addition, principles for definitions of test cases are set up including the consideration of the so-called
ônegative testing.ö
Chapter 4 describes the tests of gateway operations converting a user message from AMHS to SWIM.
Chapter 5 describes the tests of gateway operations converting a user message from SWIM to AMHS.

AMHS/SWIM Gateway supports interworking between users of the AMHS and SWIM. The gateway includes
an MTA for operations with the transfer level of the AMHS. The mapping functions of the gateway reside in

Exception handling which needs operator assistance is moved to the Control Position.
The AMHS/SWIM Gateway shall consist of the following functional building blocks:
a) AMHS Component: it is responsible for sending messages between the AMHS and the
Information Transfer and Control Unit (ITCU)
b) Information Transfer and Control Unit (ITCU): shall convert and transfer information and control
the flow of information. It performs bidirectional information mapping and address conversion
between AMQP (in the SWIM environment) and X.400 (in AMHS)
c) SWIM Component: shall interface with SWIM for exchange of aeronautical information with
SWIM information providers and consumers. It provides the interface between the ITCU and
SWIM infrastructure using AMQP.
d) Control Position (CP): stores information related with the traffic conveyed by the AMHS/SWIM
Gateway as well as the reports on issues occurred during the automated processing that need
to be attended by an operator/supervisor.
e) Directory User Agent (DUA): shall interface with the ATN Directory in order to the AMHS
address conversion. This component itÆs considered as optional.

2.1.2 IMPLEMENTATION SPECIFIC SWIM FEATURES
Typically, a SWIM implementation includes features which are either beyond the scope of the technical

generation of the related AMHS message.
2.2 MODELLING OF THE TEST ENVIRONMENT
The AMHS/SWIM Gateway Implementation Under Test (IUT) is embedded in a simulated operational
environment formed by: AMHS Test Tool with two MTA instances and SWIM Test Tool with one Message
Broker.
The MTAs have AMHS User Agents (UA) attached, which are used in submission and delivery tests.
It is also possible to make use of the IUTÆs associated Control Position û if available - to observe outcomes
of the conversion process, especially in error situations.
The Test Tool implements two MTA test applications (MTA-1 and -2) to send and receive AMHS messages
(IPM, IPN), reports and probes to and from two directions. The test tool generates AMHS data at the
X.400/P1/P3/P7 level.
The SWIM Test Tool uses Message Broker to send and receive AMQP messages.

2.2.1 WORKING POSITIONS
The scope of conformance testing includes ôconsumerö and ôproducerö SWIM components.
Notifications for specified out-of-line situations shall be sent to the Control Position of the AMHS/SWIM
Gateway.
Furthermore, traffic logs generated by the IUT during test execution shall be verified against the technical
specifications.
The format of input and presentation of test data at the above identified three working positions is seen as a
local implementation matter and is, therefore, out of scope of conformance testing. The inclusion of these
working positions in testing is limited to observation and interpretation of test data.

Below, the three types of working positions are handled in more detail.
2.2.1.1 AMQP PRODUCERS AND CONSUMERS
The SWIM Test Tool allows the generation of AMQP messages from SWIM to AMHS and in the opposite
direction the consumption of AMQP messages that shall be sent to AMQP users and which were originally
IPMs.
As part of the SWIM Test Tool, AMQP producers of SWIM information shall generate AMQP messages and
queued them in AMQP Message Broker queues. On the other hand, AMQP consumers of SWIM information
shall obtain AMQP messages of their own SWIM Message Broker queues.
This interface shall not receive IPNs, Reports or Probes as they are not conveyed in the SWIM environment.
These types of AMHS messages shall be reported and logged to Control Position.
The inclusion of consumer and producer operations in conformance testing requires operator observation
and interaction during test execution.
2.2.1.2 CONTROL POSITION
There are technical specification requirements to notify the Control Position of the AMHS/SWIM Gateway
on specified deviations from the gateway's normal operations.
Notifications may be issued for the operatorsÆ information only or may require operator assistance for
recovery from an occurred communication problem. How the Control Position is implemented is out of scope
of the technical requirements. However, the correct presentation of notifications at the IUT's Control Position
is seen as subject of conformance testing. Appropriate observations have to accompany certain test
exercises.
2.2.1.3 ACCESS TO SYSTEMS MANAGEMENT FUNCTIONS
Access to IUT's systems management functions by means of a related working position shall be possible
for:
ò Preparation of the IUT for the test configuration, and
ò Verification of traffic logs generated by the IUT during test exercises.

3 SUPPORTED SCOPE OF CONFORMANCE TESTING
3.1 GENERAL ASPECTS
The scope of testing covers the communications and interoperations between the SWIM and the AMHS by
means of the AMHS/SWIM Gateway. The AMHS interface is tested for verification of the gateway's capability
to intercommunicate with SWIM, however, it is not subject of dedicated conformance testing.
The following aspects of conformance testing shall be considered:
ò Protocol testing, encompassing AMHS to AMQP mappings (and vice versa).
ò Functionality testing, to ensure the appropriate implementation of functionalities mentioned on the
technical specification
Below, the scope of conformance testing of Gateway Operations will be specified by related test cases.
3.1.1 GATEWAY OPERATIONS
Subject of the Gateway Operations is the bi-directional conversion between AMHS and AMQP user
messages and the handling of accompanying service information, i.e., AMQP messages, AMHS IPMs,
AMHS Reports, AMHS Probes and AMHS Receipt Notifications.
Considering the functional complexity of the AMHS/SWIM Gateway, the test cases are logically subdivided
in two sub-groups:
1) Flow of messages from AMHS to SWIM, including handling of Probes, and
2) Flow of messages from SWIM to AMHS.
The two sub-groups include the handling of accompanying service information.
Regarding AMHS and SWIM, the AMHS/SWIM Gateway acts as an endpoint in exchange of information.
The address look-up tables specified in ICAO Doc 9880 Part II [1] paragraph 4.3.2 for the AFTN/AMHS
Gateway shall be used by the AMHS/SWIM Gateway for address conversion.
The IUT's capability to convert addresses in the SWIM and AMHS address spaces is tested in both sub-
groups test cases.
The parameters required for testing are defined in EUR Doc 047, AMHS/SWIM Gateway Specification.
The ITCU shall perform long-term logging for a period of at least thirty days of information related to the
following exchanges of information objects with the AMHS component and the SWIM component.
Logging requirements are defined in section 4.3.1 Traffic logging of EUR Doc 047, AMHS/SWIM Gateway
Specification. The requirements make it possible to perform message tracing when an investigation is
needed. The query of the logged information is seen as a local implementation detail.
Verification of the logged information shall be performed on any test case. For this purpose, the local query
and tracing provisions will be used. Access is typically provided at the system management interface of the
IUT.

3.2 DEFINITION OF TEST CASES
According to ISO 9646-2 a test case comprises the actions to achieve a specific test purpose.
Each test case normally has a single test purpose, such as that of verifying that the IUT has a certain required
capability (i.e., the capability to support certain message lengths) or exhibits a certain required behavior
when a particular event occurs.
There may be many criteria for methodical definitions of test cases to achieve an envisaged confidence in a
particular functional area of the IUT.
Figure 6 û Test Cases
The test categories are based on the following definitions:
ò Normal communications (N). û The Test Tools provide the IUT with correct inputs and the related
responses (behaviour) of the IUT should be in compliance with the technical specifications. It should
be noted that a correct response of the IUT not always equals to a successful transmission of a
SWIM/AMHS Information Object. For example, a valid AMQP Message could be transferred to
AMHS and be rejected by a MTA if it canÆt be routed, causing the reception of an NDR by the IUT.
The same applies to AMQP Messages transferred to AMHS and causing RN and NRN.
ò Erroneous AMQP messages (E1). û The SWIM Test Tool does not act in compliance with the
AMHS/SWIM Gateway Specification. These SWIM conventions are defined in Table 8 û 4.5.2 Use
of AMQP elements. It should be noted that violations of such AMQP conventions are not equal with
faults in the communication.
ò Procedural errors (E2). û The Test Tool does not act in compliance with the procedures, or the
arrangements made in the test configuration. Examples: 1) The Test Tool sends a message that
have a payload larger than the configured maximum number of bytes. 2) The IUT is requested to
send a message with a Report request, however, the AMHS Test Tool does not return any Report.
